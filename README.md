# 离线工单归档库

用 Python + SQLite 实现的离线工单归档库：把符合条件的工单从在线库迁移到本地
JSON 文件，并支持进程被强制终止后的自动续跑。

## 接口

```python
from ticket_archive import TicketArchive

store = TicketArchive("tickets.db", "archive_dir")
store.ImportTickets(records)          # 写入在线库，record 为含 id/status/closed_at 的 dict
files, total = store.Archive("b1", now)  # 执行一次归档，返回 (正式文件路径列表, 工单总数)
store.Recover()                       # 恢复所有已登记但未完成的批次
store.GetTicket("id")                 # 无论在线还是已归档，返回完整原始记录
```

## 选集规则

每个 `batch_id` 在**首次持久登记时**冻结选集：当时在线记录数严格大于 100000，
则选取所有 `status == "closed"` 且 `closed_at` 严格早于 `now - 90 天`
（一天固定 24 小时）的工单；否则选集为空。空选集同样形成可重放的批次结果。
同一 `batch_id` 的后续调用直接返回登记的结果，不会吸收后来导入的工单。

## 持久化边界

- **SQLite**（`tickets.db`）：
  - `tickets`：在线工单完整正文（已归档工单从此表物理删除）；
  - `batches` / `batch_items`：批次元数据与冻结选集（只有 id 与序号，无正文）；
  - `archive_index`：定位索引（ticket id → 归档文件名，无正文）。
- **归档目录**：只有以 `.json` 结尾的文件是正式归档，每个文件是可独立解析的
  JSON 数组，最多 1000 条。正式文件先写临时文件（`*.json.tmp`）、fsync 后原子
  rename 到位——一旦可见即完整，之后绝不改写。
- 每个批次的提交流水：发布正式文件 →（文件已可读）→ 在单个 SQLite 事务中
  删除在线记录并写入定位索引 → 全部文件完成后将批次标记为 `done` 并冻结结果。
  因此崩溃窗口内只允许"正式文件与在线记录短暂重叠"，绝不出现两边都缺失。

## 恢复语义

- 重新打开存储后，若存在未完成的批次，必须先成功调用 `Recover()`，
  否则其他操作抛出 `RuntimeError`。
- `Recover()` 严格按**冻结的选集**续跑：不重新统计在线记录数、不重新取当前
  时间；即使部分删除已使在线数降到 100000 以下，剩余工单仍会被归档。
- 续跑幂等：正式文件已存在则跳过写入，只补齐在线删除与定位索引；恢复自身
  被反复终止也能继续，直到批次标记为 `done`。
- 不依赖进程内进度、不需要清空归档目录或人工清理，也不会为同一记录生成
  多个正式文件。

## 运行测试

```bash
python3 -m pytest tests/ -v
```

测试覆盖：超过 100000 条在线记录、跨三个文件的选集（含 90 天边界与很早创建
的 open 工单）、逐字段读回；用环境变量 `TICKET_ARCHIVE_FAILPOINT` 武装的可控
故障点终止真实子进程（正式文件已发布但源记录未删、源记录删除已提交但调用未
返回、恢复途中再次被终止），并校验在线库与全部正式文件的并集与交集；以及
批次完成后导入新工单、重复旧 `batch_id`（含空结果批次）不会再次归档。
